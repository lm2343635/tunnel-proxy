# macOS 应用分流计划：实施就绪度评审

**评审依据**：只看了计划正文，没有核对源码、工程配置或真机行为。下文标注两类结论：

- **【确定】**：计划文本自身矛盾或遗漏，读正文即可判断。
- **【待验证】**：依赖 macOS 或目标 App 的实际行为，需要在阶段 1 实测确认。

---

## P0-1 应用身份模型自相矛盾，Helper 进程的归属规则缺失

**章节**：§1、§3.2、§7 阶段 2、§8「桌面 App 实测」

**触发场景与影响**
- 【确定】阶段 2 把身份定义为「签名身份与团队 + 选中包的校验信息」，§3.2 又要求「应用移动或更新按签名重新定位」。包校验值每次更新都会变。Chrome、Claude、ChatGPT 更新频繁，更新后规则可能失配，或频繁显示「无法识别应用」。
- 【确定】计划只在阶段 1 要求「观察」Helper，阶段 2 的模型和 §3 的界面都没有定义「父 App ↔ Helper」的映射。如果只按主包签名标识匹配，Claude Helper、Chrome 的网络服务进程等实际发起连接的进程会被当成「未添加的应用」直接放行。结果是用户设了「全部走代理」，流量却悄悄走了直连。这是最难被用户察觉的失效方式。
- 【待验证】flow metadata 中的 `sourceAppSigningIdentifier` 和 audit token 对 Electron Helper、Chrome 网络服务、WebKit Networking 进程分别给出什么。Safari 作为对照组，它的网络进程能否归属到 Safari，也要确认。

**建议修订**
- 把身份拆成两层：
  - 匹配键：Team ID 加签名标识前缀或标识集合。
  - 校验信息：仅用于「同名辨认」和「篡改提示」，不参与匹配。
- 新增「归属规则」小节，写明以下内容：
  - Helper 如何映射到父 App（同 Team ID 且标识带前缀，或从包内 Helpers 枚举）。
  - 无法归属的连接默认怎么处理。
  - 最近连接中如何显示「经由 Helper」。
- 阶段 1 的产出改为一张归属矩阵：进程 → 拿到的签名标识 → 能否归属 → 处理方式。阶段 2 以这张矩阵为输入。

**可观察验收**
- 归属矩阵覆盖 Claude、ChatGPT、Chrome、Safari 的全部联网进程。
- 将 Claude 设为「全部走代理」后，在物理网卡抓包，看不到 Claude 任一进程直连目标的 TCP 连接。
- 升级 Chrome 后规则仍然命中，界面不出现「无法识别」。

## P0-2 域名不可得时，首页示范场景失效；QUIC 会让白名单域名泄漏

**章节**：§1、§2 策略表及产品边界、§7 阶段 3

**触发场景与影响**
- 【待验证，风险高】`remoteHostname` 只在 App 按主机名发起连接时才有值。Chrome 若启用内置 DNS 解析或 DoH，送到扩展的流可能只有 IP。这会带来两个后果：
  - §1 的核心演示「Chrome 仅指定域名走代理」会全部走直连。
  - 黑名单模式则会全部走代理。
- 【确定】按 §2 的策略表，在「仅指定域名走代理」策略下，没有主机名的 UDP 流（例如 QUIC/HTTP3 的 UDP 443）落入默认列「直连」并被放行。即使 TCP 连接命中白名单，同一域名也可能通过 QUIC 直连出去，等于规则泄漏。
- 【确定】计划没有说明代理时 SOCKS5 使用「域名」类型还是「IP」类型。如果在本机解析后再按 IP 转发，会出现 DNS 泄漏和地理解析不一致。
- 【确定】如果改用读取 TLS 首包里的 SNI 来判定域名，读过数据的流就不能再交回系统。这时「直连」只能由扩展自己中继，与 §2「直连 = 交还系统」的定义冲突。

**建议修订**
- 在 §2 增加「域名可得性」分支，并明确选择以下一种做法，同时写清它对「直连」语义的影响：
  - (a) 只认 `remoteHostname`，在界面上如实提示「此 App 多为仅有 IP，域名策略效果有限」；
  - (b) 引入 SNI 判定，并定义扩展自行直连中继的语义。
- 域名策略下的 UDP：凡属同一 App 的策略含「走代理」的部分，UDP 443 应阻止或默认阻止，以迫使回退到 TCP，不能沿用 IP 默认列。
- 写明有主机名时 SOCKS5 一律使用域名类型（远端解析）。

**可观察验收**
- Chrome 在默认设置和 DoH 开启两种状态下，最近连接中有主机名的比例有记录。
- 白名单域名在 QUIC 可用的站点上，抓包看不到 UDP 443 直连。
- SSH 服务器端日志能看到 SOCKS 请求中的域名。

## P0-3 失败即阻止的边界没有收口：宿主崩溃或卸载后可能永久锁死

**章节**：§2 产品边界、§4「首次使用、恢复、退出」、§5 表格末两行

**触发场景与影响**
- 【确定】计划规定扩展在隧道断开时阻止应走代理的连接，并且只承诺「正常退出」会结束分流。下面三种情况都没有被定义：
  - 宿主崩溃或被强制退出，SSH 子进程随之结束；
  - 用户直接把 App 拖进废纸篓；
  - 扩展存活但宿主长时间不在。
- 【待验证】宿主崩溃后，透明代理配置是否保持启用，provider 是否继续运行。如果是，Claude、ChatGPT 等「全部走代理」的 App 会一直被阻止，而用户界面中已没有任何入口可以解除。
- 【确定】§5 写的是「不能把进程退出期间的保护作为承诺」，关注的是放行风险。真正需要设计的反向风险（误锁死）没有被写入。

**建议修订**
- 为 provider 定义「宿主失联」策略：例如心跳超时 N 秒后进入「放行」或「保持阻止」状态，并在计划中明确选择哪一种，并给出理由。
- 卸载说明中列出移除扩展与网络配置的步骤；如有条件，提供「卸载」菜单项。
- 宿主重新启动时必须协调 provider 状态，这一点作为启动时的首个动作。

**可观察验收**
- 分流期间用 `kill -9` 结束宿主：在约定时间内，目标 App 的行为符合所选策略；重启宿主后状态一致。
- 删除 App 后重启系统，系统设置中没有残留的启用配置，目标 App 可以联网。

## P1-4 模式切换事务缺少可实施的状态机

**章节**：§5「全局与按应用分流互换」「首次选择按应用分流」、§7 阶段 2

**触发场景与影响**
- 【确定】计划只写了「串行、协调、回读、失败恢复」，缺少以下关键定义：
  - 期望状态何时落盘（发生在系统修改之前还是之后）；
  - 每一步的超时；
  - 用户在授权对话框停留期间，再次切换或退出时怎么处理；
  - 在途连接的处理方式。
- 由此带来的后果：
  - 切换中途崩溃，重启后无法判断该回滚到哪里；
  - 从分流切到全局时，provider 停止会切断已中继的长连接（上传、下载、流式对话），与「规则只作用于新连接」的承诺冲突；
  - 全局模式下，系统 SOCKS 指向本机端口；如果两条路径短暂重叠，扩展的出站中继可能被自身或系统代理再次捕获，形成自环。
- 【待验证】provider 对本机回环地址和自身进程的排除，在 `NETransparentProxyNetworkSettings` 规则下是否可靠。

**建议修订**
- 新增显式状态机：`idle → preparing → awaitingApproval → applying → verifying → active | rolledBack | unknown`。
- 规定先写入「期望状态 + 事务 ID」再动系统设置。
- 每一步设超时，并定义取消语义。
- 写明切换时在途连接的处理：「中断并提示目标 App 重连」或「排空等待 X 秒」。
- 写明排除规则（本机回环、SSH 进程、provider 自身），并补一项自环检测。

**可观察验收**
- 在状态机每个状态注入宿主崩溃，重启后进入的状态确定且被记录。
- 下载大文件期间切换方式，界面给出与计划一致的提示。
- 两种方式互切 50 次，不出现自环，CPU 与连接数无异常增长。

## P1-5 「直连」一词承载三种含义，状态用语未统一

**章节**：§1、§2、§6.1、§6.3、§4「迷你窗口」

**触发场景与影响**
- 【确定】同一界面中「直连」同时用于三种不同含义：
  - 「本机直连 SSH 服务器」，属于 SSH 连接路径；
  - 「全部直连 / 直连」，属于应用策略和实际走向，含义是「交回系统」；
  - 「未添加的应用使用本机网络」，用的却是另一个词「本机网络」。

  §2 要求两个概念「入口、字段、日志均区分」，但用词本身没有区分。用户看到「直连」，可能误以为绕过了系统 VPN，或误以为与 SSH 路径有关。
- 【确定】§4 走查要求「这些入口使用第 6 节相同的状态词」，但 §6 没有给出一张「运行状态 → 文案 → 出现入口」的总表。「未连接」「隧道已断开」「等待隧道连接」三者的使用边界不清。

**建议修订**
- 应用分流统一使用「不经隧道 / Not via tunnel」或「系统网络 / System network」，在悬停说明中解释「仍受系统 VPN 和代理影响」。SSH 路径保留「直连」。
- 补一张状态词矩阵：行是隧道状态与分流状态的组合，列是主页、弹窗、迷你窗口、菜单栏、日志。

**可观察验收**
- 两种语言的全部截图中，同一状态在各入口用词一致。
- 文案检查脚本确认「直连」只出现在 SSH 路径相关的 key 中。

## P1-6 测试缺口：缺少泄漏判定、平台矩阵、性能和统一日志隐私检查

**章节**：§8 全部、§3.6、§7 各阶段证据

**触发场景与影响**
- 【确定】验收依赖「可控出口 + 连接事件交叉确认」，但没有把「物理网卡零直连」作为通过标准。P0-1、P0-2 类型的泄漏无法被判定为失败。
- 【确定】计划没有列出以下验收维度：
  - macOS 版本矩阵（14 / 15 / 26）与 Apple 芯片 / Intel；
  - 与第三方 VPN 或其他透明代理共存；
  - IPv6 单栈；
  - 中继的吞吐、延迟、内存和并发上限；
  - 50 条缓冲在高峰下的表现。
- 【确定】§3.6 承诺「常规文本日志无逐站记录」，但没有覆盖扩展写入的 `os_log` 统一日志，那里可能留下主机名。
- 【确定】没有分层的自动化测试策略：哪些在 CI 中用模拟 provider 运行，哪些只能在已签名的真机上运行。

**建议修订**
- §8 新增「泄漏测试」行：使用 `pf` 或抓包，以「被判定走代理的 App 在物理接口上的目标连接数为 0」为通过标准。
- 新增平台与共存矩阵和性能基线，例如中继吞吐不低于直接经 SOCKS 的 X%，扩展内存不超过 Y MB。
- 隐私检查加入 `log show --predicate 'subsystem == …'`，并确认日志使用 `%{private}` 修饰。
- §7 写明测试分层，以及每一层可在 CI 中运行的范围。

**可观察验收**
- 交付记录包含矩阵中每一格的结果或「未测」标记。
- 统一日志中检索测试域名，命中数为 0。

## P2-7 英文作 key 的短词冲突与复数 key 回退风险

**章节**：§6 开头、§6.1 复数段、§6.3、§6.5

**触发场景与影响**
- 【确定】「Direct」「Failed」「Add」「Apps」「Time」「Turn Off」这类短英文 key 在不同语境下无法分别翻译。例如「Failed」在既有界面中可能译为「失败」，这里需要译为「连接失败」。计划还明确写了「Direct 复用项目已有 key」，会把旧语境的译文带进新界面。
- 【确定】`routing.appCount` 是全项目唯一的非英文 key。如果英文的 stringsdict 缺失或者 bundle 选错，界面会直接显示 `routing.appCount`。
- 【确定】中文标点不统一：部分英文带句号的条目，中文没有句号，例如「未添加的应用使用本机网络」「其他域名或仅有 IP 时直连」。
- 【待验证】在 SwiftUI 中，用 `String` 变量传给 `Text` 时不会自动本地化（计划已提及），需要逐处确认。

**建议修订**
- 新增或语境不同的短词改用带语境的 key，例如 `route.failed`，或使用独立的 `.strings` 表，并为每个 key 附上译者注释。
- 构建阶段加入缺键和 key 外露检查。
- 统一句末标点规则：完整句加句号，标签不加。

**可观察验收**
- 用伪本地化或缺键模式运行时，没有任何 key 原文外露。
- 两种语言的字符串表 diff 中，每个 key 都有对应项和注释。

## P2-8 默认行为与语音类 UDP 的取舍尚未定型，主页摘要可能误导

**章节**：§3.2、§3.4、§2 UDP 边界、§6.1 应用数

**触发场景与影响**
- 【待验证】ChatGPT、Claude 的语音或实时功能如果使用 WebRTC/UDP，在「全部走代理」策略下会被阻止，功能直接不可用。计划只要求「记录覆盖」，没有给用户提示或说明。
- 【确定】主页摘要的应用数「含显式配置为直连的应用」。新添加的应用默认就是「全部直连」，所以摘要显示「3 个应用」时，实际走代理的可能是 0 个，容易让用户误以为分流已经在起作用。

**建议修订**
- 摘要拆成「N 个应用 · M 个走代理」。
- 在 UDP 被阻止的原因提示中加入「语音、视频等功能可能不可用」，手册排障章节对应补充。

**可观察验收**
- 只添加「全部直连」的应用时，主页明确显示「0 个走代理」。
- ChatGPT 语音在「全部走代理」下的表现，有记录并在手册中说明。

## 阶段就绪判断

| 阶段 | 判断 | 前置条件 |
|---|---|---|
| 1 · 平台能力验证 | **可立即开始，且应作为闸门** | 产出物补充：归属矩阵（P0-1）、主机名可得率与 QUIC 行为（P0-2）、宿主失联时 provider 的行为（P0-3） |
| 2 · 模型与控制器 | **有条件就绪** | 先修订身份模型和切换状态机（P0-1、P1-4）。迁移和域名归一化部分现在即可开工 |
| 3 · 转发与活动 | **未就绪** | 依赖阶段 1 结论，以及 P0-2、P0-3 的设计决定 |
| 4 · 界面与翻译 | **可并行搭建布局** | 文案在 P1-5、P2-7、P2-8 定稿前不宜冻结 |
| 5 · 恢复、文档与发布 | **未就绪** | 卸载与失联语义未定，签名和公证链路未验证 |

**总体结论**：计划在界面范围、入口联动和隐私边界上写得完整。但应用归属和域名可得性这两项核心前提尚未验证，失败即阻止的收口也不完整。当前只适合启动阶段 1 和不依赖扩展的离线部分，**整体尚未达到实施就绪**。建议阶段 1 结束后，根据实测结果修订 §2、§3、§5、§8，再做一次评审，然后进入阶段 3。

# 第二轮评审：macOS 桌面应用分流实施计划

## 一、实施就绪判断

- **第一阶段：** 有条件可开始。
  - V1、V2、V4 的主体用例现在就能在最小原型上跑。
  - 先用约半天修改文档，补齐下文第 1–3 项。原因有两个：
    - 一是让 V3、V5 有明确的判定标准；
    - 二是让 V5、V7、V8 能用最小原型执行。
  - 否则这几项跑完也无法判定通过或失败。
- **后续阶段：**
  - 第 2 阶段的模型、迁移和本地化，以及第 4 阶段的模拟 UI，可按计划与第一阶段并行。
  - 第 3 阶段的正式转发须满足以下条件后才能开始：
    - V1、V4 和 V5 原型部分在目标系统组合上通过；
    - 正式转发只覆盖 V2、V3 通过的 App 和策略。
  - 对外声明支持，须等产品版和发布包按第 8 节复跑。

## 三、仍存在的矛盾或验收缺口（按严重度）

### 1. 【高 · 文档缺陷，跑第一阶段前必须修】分流切换期间可能直出，且没有通过标准

- **矛盾所在：** §5.1 写"目标就绪前保留旧方式"。同节又写"从全局进入时……撤销本应用持有的 SOCKS，再激活分流"，离开分流时则"撤销分流并确认，再按目标启用系统 SOCKS"。两种写法互相矛盾。V5 只要求"记录出口与持续时间"，没有给出判定阈值。
- **触发场景：** 全局代理与按应用分流互换时，某个设为"全部走代理"的 App 正在发起新连接。
- **用户影响：** 用户本意是全程走隧道，但在空档期内连接会经本机出口直出，可能暴露真实 IP 或触发风控。而界面只显示"正在切换"。
- **最低修订：** 二选一，并写入 V5 的通过标准。
  - **方案一：** 规定切换期间，对新旧两种方式都判定应代理的流，本机直达连接数须为零。可行做法是先激活分流再撤销 SOCKS。由于中继端点已被排除，两条路径可以短暂并存。
  - **方案二：** 明确接受一个时长上限的直出窗口，并在切换确认文案中告知用户。

### 2. 【高 · 文档缺陷，跑第一阶段前必须修】本地、局域网目的地和 App 自发 DNS 不在决策表内

- **缺口所在：** §2.2 的决策表只区分"已知域名命中、已知域名未命中、只有 IP"三列，没有回环、链路本地、私有网段、组播目的地的行。
- **触发场景：**
  - Chrome 设为白名单后，访问 `localhost:3000` 或路由器 `192.168.1.1`。这类连接没有主机名，按决策表直接"阻止"。
  - 设为"全部走代理"的 App 访问本机 MCP 或 LAN 服务，会被送到 SSH 出口，结果失败。
  - App 自己发出的 UDP 53 查询，在"代理"判定下也会被阻止，导致解析失败。
- **用户影响：** 本机开发、局域网设备、部分 App 的解析功能直接不可用。用户看到的只是"已阻止"或"连接失败"。
- **最低修订：**
  - 在决策表前加一条"目的地类别"预判：回环、链路本地、组播默认交回系统，私有网段默认走向也要写明。
  - 写明 App 自发 DNS（UDP、TCP 53，以及 DoH）在四种策略下的结果。
  - V3 增加 localhost、LAN IP、App 自发 DNS 三个用例，并写出预期结果。

### 3. 【高 · 文档缺陷，跑第一阶段前必须修】V5、V7、V8 超出"最小原型"的执行能力

- **矛盾所在：** §7.1 规定原型"只实现支撑实验的控制通道、可观测事件与中继"。但以下三项都要求产品级能力：
  - **V5** 要求覆盖三种方式的六个切换方向、5 个注入点、持久事务重启复原、端口变更、50 次互切。这实际上是第 2 阶段控制器的完整功能。
  - **V7** 要检查每 App 50 条的缓冲、统计、CSV、规则持久化。
  - **V8** 要求"各入口符合第 5.3 节""无裸 key"。
- **后果：** 第 3 阶段又以 V5 通过为前提，形成循环依赖。
- **最低修订：** 把这三项拆成原型部分（a）和产品部分（b）。

| 编号 | 原型部分（a）：第一阶段在最小原型上执行 | 产品部分（b）：移到阶段 2–4 |
|---|---|---|
| V5 | 自环检查、provider 启停与系统 SOCKS 的交接空档测量、最简版本计数下的陈旧回执 | 完整事务、注入点、端口变更 |
| V7 | 中继性能、原型的统一日志与崩溃诊断 | 缓冲上限、统计、CSV、持久化隐私 |
| V8 | 真实系统面板的审批与撤销，以及不运行宿主时的恢复路径 | 双语 UI 状态 |

  - 还要写明：第 3 阶段的门槛只看 V5a；V5b 是正式转发定型的门槛。

### 4. 【中 · 设计缺口，用例在第一阶段前补，修复可随验证进行】SOCKS 监听的归属未在扩展侧校验

- **缺口所在：** §5.2 只在"宿主重启后"才"核实名下 SOCKS 监听"。
- **触发场景：** 隧道进程退出、端口被释放后，在宿主或心跳发现之前（最长约 15 秒，或隧道断开但宿主未及通知），另一个本地进程绑定了同一个端口。
- **用户影响：** 应代理的流量，连同 SOCKS 请求里的域名，会被交给不受信任的监听者。这既是泄露，也违背"禁止直连回退"的承诺。
- **最低修订：** 每条中继都须验证监听方身份，例如核对监听进程的审计令牌，或使用会话级 SOCKS 认证；验证失败按"隧道不可用"阻止。V4 增加"断开后第三方占用该端口"的用例。

### 5. 【中 · 验收缺口，可随验证补】规则版本与活动连接的可见性

- **缺口所在：** §3.5 和 §5.1 写"编辑规则只影响新连接"，但 §3.6 的事件字段只有"时间、应用身份、目的主机或 IP、协议、判定与原因"，没有规则版本和会话 ID。V1–V8 也没有"在途连接期间改规则"的用例，V5 只覆盖切换方式。
- **触发场景：** Chrome 复用长寿命的 HTTP/2 直连。用户把这个域名加入白名单，界面显示"规则已生效"，但流量仍然直出。
- **用户影响：** "实际走向"表里新旧判定混在一起，用户无法分辨"规则没生效"和"旧连接仍在用"。
- **最低修订：**
  - 事件携带规则版本，界面标出生效时间分界。
  - V3 增加一个用例：应用新规则后，旧连接仍保持原走向，新连接按新版本判定，且事件版本号与扩展确认的版本号一致。

### 6. 【低 · 验收缺口，可随验证补】IPv6 场景下的出口能力是测试前提，但没有列出

- **缺口所在：** V6 要测"IPv6 单栈"，V3 要核对 IPv6 地址类型。但测试条件只要求受控站点支持 IPv4/IPv6，没有要求 SSH 出口具备 IPv6 能力。
- **触发场景：** SSH 节点只支持 IPv4 时，黑名单模式下仅有 IPv6 地址的流，以及单栈环境下的代理流，都会"连接失败"。
- **用户影响：** 这类失败可能被误判为扩展缺陷，或被误记成"已阻止"而通过。
- **最低修订：** 测试条件中写明 SSH 出口的 IP 版本能力。出口不具备时，相关用例记"未测"，不得记"通过"。

## 四、不属于设计缺陷、已妥善安排的待验证项

以下内容依赖真机实测，计划已给出失败后的范围收缩路径，不应视为设计缺陷：

- Chrome 或桌面 App 能否取得主机名（V3，未通过则只评估全 App 策略）。
- Helper 和共享服务的归属完整性（V2，未通过则在覆盖表和 UI 标出限制）。
- 强退宿主后扩展是否存活，以及系统面板的恢复路径（V4，无法解除拦截则阻止该版本发布）。
- 与 VPN 或其他透明代理的共存（V6）。
- 中继性能（V7）。
- 语音、WebRTC 受 UDP 阻止的影响（V8）。
